# 직원 등급 (대표원장 / 부원장 / 팀장 / 사원) — 설계 문서

- 날짜: 2026-09-19
- 상태: 승인 대기
- 범위: 가입 승인된 직원에게 등급을 지정·변경할 수 있게 한다. **화면별 열람 권한 제한은 이번 범위가 아니다**(나중에 등급 기준으로 별도 작업).

## 1. 배경 / 목적

지금 `staff.role`은 `owner` / `staff` 두 값뿐이다. 앞으로 대표원장·부원장이 볼 수 있는 내용과, 팀장·사원까지 순차적으로 볼 수 있는 내용을 나누려고 한다. 그 전에 먼저 직원마다 등급을 저장하고, 대표원장이 가입 승인 때 지정하고 이후에도 바꿀 수 있어야 한다.

## 2. 결정 사항 (사용자 확인 완료)

- 등급은 4단계, 높은 순서: **대표원장 > 부원장 > 팀장 > 사원**
- 부원장은 **볼 수만 있고 관리는 대표원장만** 한다 — 직원 가입 승인, 등급 지정, 월 목표 입력 등 지금 `owner` 전용인 기능은 그대로 대표원장만 쓴다.
- 등급은 **승인할 때 지정**하고, **이후에도 변경 가능**하다.
- 가입 신청자가 등급을 직접 고르지는 않는다.

## 3. 접근 방식

`staff.role`(관리 권한 `owner`/`staff`)은 그대로 두고, 등급을 별도 컬럼 `grade`로 추가한다. 기존 코드 20여 곳의 `role === 'owner'` 검사를 건드리지 않아 안전하다. 두 값이 어긋나지 않도록 DB 제약으로 "대표원장 등급일 때만 `role = 'owner'`"를 강제한다.

(`role` 자체를 4단계로 늘리는 안은 기존 검사·RLS·승인 API를 전부 고쳐야 해서 채택하지 않았다.)

## 4. 데이터 모델

`staff` 테이블에 컬럼 추가:

| 컬럼 | 타입 | 설명 |
|---|---|---|
| grade | text, not null, default '사원', check in ('대표원장','부원장','팀장','사원') | 직원 등급 |

- 기존 `role = 'owner'` 행은 `grade = '대표원장'`으로 채운다(백필). 이미 승인된 나머지 직원은 기본값 `사원`으로 시작하고 대표원장이 화면에서 조정한다.
- 제약: `check ((role = 'owner') = (grade = '대표원장'))` — 관리 권한과 등급이 어긋나는 행을 DB가 거부한다.
- 신규 가입은 기존처럼 `role = 'staff'`, `status = 'pending'`, `grade = '사원'`으로 들어온다(`/api/signup` 변경 없음).
- 마이그레이션 순서: ① 컬럼 추가 → ② `role = 'owner'` 행을 `대표원장`으로 백필 → ③ 제약 추가. 백필 전에 제약을 걸면 기존 원장 행이 제약에 걸려 실패한다.
- 제약이 생긴 뒤에는 `role = 'owner'` 계정을 직접 만드는 스크립트(시드·테스트용)가 `grade = '대표원장'`도 같이 넣어야 한다. 넣지 않으면 기본값 `사원`과 어긋나 삽입이 거부된다.
- 마이그레이션은 `supabase/migration_staff_grade.sql`로 두고 `schema.sql`에도 같은 내용을 반영한다(둘 다 idempotent).

## 5. 보안

- 일반 로그인 계정은 이미 `staff.name` 컬럼만 수정할 수 있게 컬럼 단위로 제한돼 있다(`grant update (name)`). `grade`는 이 목록에 없으므로 **직접 올릴 수 없다.**
- 등급 변경은 서버 API에서만 한다. 요청자가 로그인된 승인 완료 `owner`인지 서버에서 직접 확인한 뒤 service_role로 갱신한다(기존 `/api/staff/approve`와 같은 방식).
- **대표원장 행의 등급은 API가 거부한다.** 화면에서 대표원장을 만들거나 내리는 기능은 없다(제약 위반도 막고, 마지막 대표원장이 사라지는 사고도 막는다). 지정 가능한 값은 부원장/팀장/사원 세 가지뿐이다.

## 6. API

- `POST /api/staff/approve` — 요청 본문에 `grade`(부원장/팀장/사원, 생략 시 사원)를 받아 승인과 등급을 함께 저장한다. 기존 동작(대표원장만 호출 가능)은 유지.
- `POST /api/staff/grade` (신규) — `{ staffId, grade }`로 이미 승인된 직원의 등급을 바꾼다. 대표원장만 호출 가능. 대상이 대표원장이거나 `grade`가 허용값이 아니면 400.

두 API의 등급 검증은 공용 함수 하나(`isAssignableGrade`)를 쓴다.

## 7. 화면

- **직원 승인 페이지** (`/staff-approval`): 승인 대기 목록의 각 행에 등급 선택(기본 `사원`)과 승인 버튼. "사용 중인 계정" 목록의 각 행에는 등급 선택 드롭다운을 두어 언제든 바꿀 수 있게 한다. 대표원장 행은 드롭다운 없이 "대표원장"으로만 표시한다. 지금 이 목록이 `원장`/`직원`으로 표시하는 부분을 등급 표시로 바꾼다.
- **상단바**: 이름 옆에 등급을 작게 표시한다(예: `김동규 · 대표원장`).

## 8. 나중을 위한 준비 (이번에 사용하지는 않음)

`src/lib/staffGrade.ts`에 등급 목록, 순서, 판정 함수를 둔다.

- `GRADES`: 높은 순서 배열
- `isAssignableGrade(value)`: 부원장/팀장/사원인지
- `gradeAtLeast(grade, min)`: `grade`가 `min` 이상인지 (예: 팀장 이상만 볼 수 있는 화면을 나중에 만들 때 사용)

화면별 열람 제한은 이 함수를 쓰는 후속 작업으로 남긴다.

## 9. 테스트

- `staffGrade.ts`의 순서·판정 함수는 Vitest로 검증한다(경계: 같은 등급, 최상/최하 등급, 알 수 없는 값).
- API 권한(원장 아님 거부, 대표원장 행 변경 거부, 허용되지 않는 등급 거부)과 제약 동작은 실제 DB에 임시 계정을 만들어 확인하고 정리한다.

## 10. 이번 범위 아님

- 화면·데이터별 열람 권한 제한(등급 기준) — 후속 작업
- 가입 신청 시 직원이 직접 등급 선택
- 대표원장 승격/강등 화면
- 등급별 관리 권한(부원장에게 승인 권한 위임 등)

## 11. 미해결 / 확인 필요

- 화면 문구 중 "원장만 볼 수 있는 화면이에요" 같은 표현은 이번에 바꾸지 않는다(권한은 여전히 `owner` 기준). 등급 기반 열람 제한을 만들 때 함께 정리한다.
